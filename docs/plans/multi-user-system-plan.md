# 多用户系统改造规划

> 状态：阶段 2（用户数据隔离）已落地；管理员用户管理 Web 尚未开始
>
> 目标：在保留现有单管理员认证和 SQLite 部署能力的基础上，逐步改造为支持管理员、普通用户和用户数据隔离的多用户系统。

## 1. 当前基础与改造边界

当前项目已经具备 FastAPI、Web 登录页、Cookie 会话、认证中间件和 SQLite 数据库。认证实现位于 `src/auth.py`、`api/v1/endpoints/auth.py` 和 `api/middlewares/auth.py`，由 `ADMIN_AUTH_ENABLED` 控制。

当前认证仍是单管理员模式：

- 管理员密码保存在数据目录中的 `.admin_password_hash` 文件。
- 没有独立的用户表、角色表和用户会话表。
- `owner_id`、`user_id` 等字段只在部分业务模块存在，尚未统一绑定到真实登录用户。
- 认证开启后主要保护 `/api/v1/*`，不能直接等同于完整的多用户数据权限体系。

本次规划只覆盖应用层多用户能力，不包含交易执行、支付订阅、开放注册和第三方 OAuth。

## 2. 建设目标

### 2.1 用户能力

- 管理员和普通用户独立登录、退出和修改密码。
- 管理员创建、禁用、启用和删除普通用户。
- 管理员重置用户密码并撤销用户会话。
- 保存用户的个人偏好、默认市场和界面设置。

### 2.2 数据隔离

用户之间必须隔离以下数据：

- 分析历史和报告。
- 自选股和关注列表。
- 投资组合、账户、交易记录和现金流水。
- 预警规则及通知记录。
- DecisionSignal 决策信号。
- Agent 问股会话和用户使用量。

以下数据继续作为公共数据共享：

- 股票行情和基础资料。
- 市场指数和市场阶段数据。
- 新闻缓存和公共情报源。
- 系统级模型、数据源和通知配置。

## 3. 推荐权限模型

第一期只实现两个角色：

| 角色 | 权限 |
| --- | --- |
| `admin` | 用户管理、系统配置、模型配置、全局运行状态和审计记录 |
| `user` | 使用分析、查看公共行情、管理自己的业务数据 |

后续如确有需要，再扩展 `readonly` 或组织管理员角色。权限判断应集中在依赖函数和服务层，不在每个接口中临时拼接条件。

## 4. 认证与会话设计

建议继续使用 HttpOnly Cookie，不引入 JWT。

推荐流程：

```text
用户登录
  -> 服务端校验密码
  -> 创建随机 Session Token
  -> 数据库只保存 Token 哈希
  -> 浏览器保存 HttpOnly Cookie
  -> 请求通过 Session 获取 user_id 和 role
```

规则：

- `user_id` 必须从服务端会话获取，禁止信任请求体或查询参数中的用户标识。
- Cookie 使用 `HttpOnly`、`Secure`、`SameSite=Lax` 和明确过期时间。
- 保留现有登录限流和密码强度校验。
- 用户禁用、退出全部设备或修改密码后，已有会话必须失效。
- 访问其他用户数据时建议返回 404，避免暴露资源是否存在。
- 在 Traefik 反向代理下验证 `X-Forwarded-Proto`、真实客户端 IP 和 Secure Cookie 行为。

## 5. 数据库设计

### 5.1 新增表

#### `users`

建议字段：

```text
id
username
email                 # 可选，第一期可不启用邮箱登录
password_hash
role
status                # active / disabled
created_at
updated_at
last_login_at
```

约束：`username` 唯一，禁用用户不能登录，密码不得明文存储。

#### `user_sessions`

```text
id
user_id
token_hash
expires_at
last_seen_at
revoked_at
ip_address
user_agent
created_at
```

应为 `user_id`、`token_hash`、`expires_at` 建立索引。

#### `user_preferences`

用于保存语言、主题、默认市场、默认报告语言和界面偏好。系统密钥和模型密钥不应存放在普通用户偏好中。

#### `audit_logs`

记录登录、失败登录、创建用户、禁用用户、重置密码、修改权限和删除用户数据等安全事件。

### 5.2 现有表改造

对用户私有业务表增加非空 `user_id`，并建立索引。改造顺序建议为：

1. 分析历史、报告和任务记录。
2. 自选股、持仓和账户数据。
3. 预警规则和通知记录。
4. Agent 会话、决策信号和使用量记录。

现有 `owner_id` 等字段需要先完成含义盘点，再决定兼容、重命名或迁移到统一的 `user_id`，不能直接把外部平台用户标识当作本地认证用户。

## 6. API 改造

保留现有认证接口，并补充：

```text
GET    /api/v1/auth/me
POST   /api/v1/auth/logout-all
GET    /api/v1/admin/users
POST   /api/v1/admin/users
PATCH  /api/v1/admin/users/{id}
DELETE /api/v1/admin/users/{id}
POST   /api/v1/admin/users/{id}/reset-password
```

业务接口统一通过当前用户依赖获得身份：

```python
current_user = get_current_user(request)
records = repository.list(user_id=current_user.id)
```

仓储层的查询、创建、更新和删除方法必须显式接收 `user_id`。不能只在 Web 页面隐藏数据，也不能只依赖前端传入的 `owner_id`。

## 7. Web 前端改造

新增页面或区域：

- 用户登录和首次密码设置。
- 个人中心。
- 修改密码和退出全部设备。
- 管理员用户管理。
- 用户状态、角色、最后登录时间和操作记录。

现有页面需要接入当前用户上下文，并确认以下页面不会读取全局数据：

- 首页分析。
- 历史记录。
- 自选股。
- 持仓。
- 预警。
- 问股会话。
- 使用量统计。

## 8. 分阶段实施计划

### 阶段 0：盘点与备份

- 导出现有 SQLite 表结构和数据量。
- 盘点每张表的公共数据、用户数据和历史兼容字段。
- 备份服务器 `data/`、`.env` 和当前镜像版本。
- 增加迁移脚本和恢复说明。

交付物：数据归属清单、迁移草案、备份与回滚步骤。

### 阶段 1：认证核心

- 新增 `users`、`user_sessions`、`audit_logs`。
- 将现有管理员密码迁移为初始 `admin` 用户。
- 增加登录、退出、当前用户和修改密码接口。
- 增加用户角色和状态校验。
- 保留单管理员兼容模式，确保桌面端和本地部署不被一次性破坏。

### 阶段 2：用户数据隔离

- 优先改造分析历史、自选股、持仓、预警和问股会话。
- 所有 Repository 增加 `user_id` 条件。
- 后台任务、流式任务和报告生成链路传递用户上下文。
- 将用户报告和运行产物按用户归属管理。

### 阶段 3：管理员后台

- 用户列表、创建、禁用、启用和删除。
- 重置密码和撤销会话。
- 查看登录时间和安全审计记录。
- 系统配置继续只允许管理员修改。

### 阶段 4：上线验证

- 在独立数据库副本执行迁移。
- 先使用测试用户 A/B 完成隔离验收。
- 灰度启用多用户模式。
- 观察登录失败、数据库锁、任务队列和通知异常。
- 通过备份验证回滚和恢复流程。

## 9. 配置与部署策略

建议增加配置项，并同步更新 `.env.example` 和部署文档：

```env
AUTH_MODE=single_admin
ADMIN_SESSION_MAX_AGE_HOURS=24
```

推荐配置语义：

- `single_admin`：保持现有单管理员模式，兼容本地和桌面端。
- `multi_user`：启用用户表、用户会话和数据隔离。

服务器切换到多用户模式前，应先完成管理员用户迁移和数据库备份。运行时请显式设置：

```env
AUTH_MODE=single_admin   # 灰度：仅 admin，禁止创建额外用户
# AUTH_MODE=multi_user   # 验收通过后切换：允许管理员创建用户
```

未设置 `AUTH_MODE` 时默认 `multi_user`（兼容阶段 3 已部署环境）。SQLite 可用于初期内部使用；当并发用户、后台任务和写入量增加后，再迁移 PostgreSQL。详细步骤见 [multi-user-cutover.md](./multi-user-cutover.md)。

## 10. 安全与稳定性要求

- 第一阶段关闭开放注册，由管理员创建用户。
- 模型 API Key、数据源 Token 和通知密钥只允许管理员配置。
- 普通用户不得读取系统配置明文或敏感环境变量。
- 登录、密码修改和管理员操作写入审计日志。
- 对跨用户读、改、删接口编写回归测试。
- 后台任务不能因为缺少用户上下文而回退到全局数据。
- 用户删除默认采用软删除；彻底删除需要单独的管理员确认流程。
- SQLite 运行时保持 WAL、定期备份和恢复演练。

## 11. 验收标准

### 功能验收

- 管理员可以创建普通用户。
- 两个普通用户可以分别登录。
- 用户 A 看不到用户 B 的历史、持仓、预警和会话。
- 禁用用户后无法继续调用业务 API。
- 管理员可以重置密码并撤销全部会话。
- Docker 重启后用户和业务数据仍然存在。

### 技术验收

- 认证、迁移和关键 Repository 有单元测试。
- 至少有一组用户 A/B 的跨用户访问测试。
- Web 构建和后端 CI 通过。
- SQLite 备份、恢复和回滚路径经过实际演练。
- API、Web、桌面端对认证状态和错误码保持一致。

## 12. 第一阶段建议范围

推荐先落地以下最小版本：

> 管理员创建用户 → 用户登录 → 用户数据隔离 → 管理员禁用用户。

暂不实现开放注册、邮箱找回密码、第三方 OAuth、订阅计费、组织租户和用户自定义 AI Key。这样可以先控制安全风险和数据库迁移范围，再根据实际用户数量扩展权限模型。

## 13. 回滚方案

- 代码回滚：恢复到上一版镜像或应用版本。
- 配置回滚：将 `AUTH_MODE` 恢复为 `single_admin`。
- 数据回滚：仅在确认迁移写入不可逆或数据损坏时，从停机前备份恢复 SQLite 数据目录。
- 不建议直接使用旧版本程序读写已经完成破坏性迁移的数据库；数据库迁移应优先采用新增字段、兼容读取和可重复执行脚本。
