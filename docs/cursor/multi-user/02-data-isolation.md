# Cursor 提词 02：用户数据隔离

## 前置条件

必须先完成阶段 0 的数据盘点和阶段 1 的认证核心。阶段 1 的认证测试未通过时，不得开始本阶段。

## 提词正文

```text
你正在维护 daily_stock_analysis 项目。先读取 AGENTS.md、docs/plans/multi-user-system-plan.md、阶段 0 数据归属清单和阶段 1 认证实现。

本阶段目标：把已确认的用户私有数据接入当前用户上下文，实现后端、Repository、后台任务、流式任务和报告文件的真实隔离。

先做一次影响面复核：

1. 列出阶段 0 标记为 user-owned 的表、Repository、API endpoint、schema、前端 store 和后台任务。
2. 确认 public 表不能误加 user_id：股票行情、指数、基础资料、新闻缓存和公共情报源继续共享。
3. 确认 owner_id、platform user_id、chat user_id 的含义；只有确定代表本地账号的数据才能迁移到 user_id。
4. 检查现有测试是否 mock 掉了 Repository 或认证层；跨用户测试必须经过真实 API -> service -> repository 路径。

迁移要求：

- 使用项目已有的数据库迁移/初始化方式；如果没有版本化迁移机制，先补一个可重复执行、可记录版本、支持失败恢复的最小迁移机制。
- 迁移必须优先采用新增字段、兼容读取和分步回填，不能直接删除旧字段或覆盖旧数据。
- 现有历史数据默认归属到迁移时的初始 admin，无法安全判断归属的数据必须进入待处理清单，不能静默分配给随机用户。
- user_id 需要非空时，先完成回填和校验，再建立 NOT NULL/外键/索引约束。
- 迁移前后都提供数据库备份和校验命令。

代码要求：

- 所有 user-owned Repository 的 list/get/create/update/delete 方法显式接收 user_id。
- 单条资源查询、更新、删除必须同时按 resource_id 和 user_id 过滤。
- 业务接口从 current_user 获取 user_id，不接受前端传入的 owner_id 作为权限依据。
- 用户访问其他用户资源时返回稳定的 404 或项目约定错误，不泄漏资源存在性。
- 后台任务、任务状态轮询、SSE/stream、报告生成和异步通知必须携带 user_id；缺少用户上下文时 fail-closed，不得回退到全局用户。
- 用户报告和运行产物按用户归属保存或在数据库中记录 owner，不能仅靠文件名猜测归属。
- 系统级配置和模型密钥只允许 admin；普通用户只能访问允许公开的脱敏配置。

优先改造范围：

1. 分析历史、报告和任务记录。
2. 自选股、持仓、账户和交易记录。
3. 预警规则、触发记录和通知记录。
4. Agent 会话、DecisionSignal 和用户使用量。

每完成一类数据，补充：

- Repository 单元测试。
- API 权限测试。
- 用户 A/B 交叉访问测试。
- 迁移前后数据计数和归属校验。

禁止：

- 只在前端隐藏其他用户数据。
- 只在路由层做一次权限判断而让 Repository 继续按全局查询。
- 用 broad fallback、空列表或 None 掩盖越权和缺少 user_id。
- 为了通过测试 mock 掉真实数据库或认证上下文。
- 同时重构无关的数据源、报告渲染或通知实现。

完成后更新相关 API schema、前端类型、docs/CHANGELOG.md 和用户数据迁移文档。运行后端 CI、非网络 pytest、变更 Python 文件 py_compile；若修改 Web，运行 Web lint/build。

交付时说明：每类表的 user_id 迁移结果、旧数据归属、权限覆盖矩阵、跨用户测试证据、未覆盖的异步路径、风险和回滚方式。
```

## 阶段验收

- 用户 A 无法读、改、删用户 B 的私有资源。
- public 数据仍可被所有已授权用户读取。
- 旧数据有明确归属，不存在静默随机分配。
- 后台任务和流式任务不会丢失 user_id。
- 迁移可重复执行，备份和回滚命令可用。
